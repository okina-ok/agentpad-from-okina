# agentpad13 调研报告

> 调研日期：2026-08-07　|　来源：[yuz207/agentpad13](https://github.com/yuz207/agentpad13)（公开）
> 结论：**不直接采用**，作为"打板 + 状态协议 + 固件工程化"的参考；主机侧我们已有更完整实现。

---

## 1. 项目是什么

开源 13 键 agent 工作键盘（macropad），从零做的完整产品：

- 裸 RP2040 + USB-C，12×1U + 1×2U 热插拔（MX）轴
- EC11 可按下旋钮 + YA13 模拟两轴摇杆 + TTP223 电容触摸键
- 24 颗 RGB：14 颗每键（含 1 颗层指示灯）+ 10 颗底光
- 固件走 **Raw HID 状态协议**：主机把每个 LED 的颜色直接推给键盘
- 完整开源：KiCad 工程、Gerber、贴片 BOM/坐标、外壳 STL/STEP、键帽、预编译固件

## 4. Raw HID 状态协议（重点借鉴）

32 字节固定帧、无 Report ID。描述符固定：Usage Page `0xFF60` / Usage `0x61`、
VID `0xFEED` / PID `0x4C4D`（QMK 默认值，显式声明防漂移）。

| 命令 | 内容 | 说明 |
| --- | --- | --- |
| `0x01 SET_KEY` | `{LED序号, r, g, b, 效果}` | 按 **灯链序号** 寻址（0-23），主机显式推颜色 |
| `0x02 SET_LAYER` | `{n}` | 主机切层（0-7） |
| `0x03 CLEAR` | 无 | 清空全部状态 |
| `0x04 PING` | `{token}` | 握手 → 设备回 CAPS：`{0x04, token, 'L','D', ver=0, led_count=24, layer_count=8, features=0x1F}` |

效果：`0` 常亮 / `1` 呼吸 / `2` 闪烁，动画在设备端做（纯整数数学，无依赖）。

设计要点：

- **寻址按链序**：`keyboard.json` 里 `rgb_matrix.layout` 按链序写，链序号 == RGB 矩阵序号，
  固件无需重映射 —— 主机侧寻址简单。
- **CAPS 握手**：主机发 PING 就能拿到设备能力（灯数/层数/特性位），支持即插即用发现。
- **效果放设备端**：主机只发静态颜色 + 效果枚举，动画由设备本地生成，节省 USB 带宽。
- **与 VIA/Vial 共存**：VIA 的 raw_hid_receive 会吞 0x01-0x04，作者打了 23 行补丁
  （`via_command_kb` 预钩子）按字节内容仲裁；三个字节级歧义冲突有文档化处置。
- **一致性测试**：把真实固件 C 代码在主机编译，用协议 oracle 造的帧驱动并逐字节断言，
  这是"协议锁定"的工程化做法，很值得学。

## 5. 固件方案

- QMK / vial-qmk 键盘树，预编译 `.uf2`（拖进 RPI-RP2 即刷，不擦用户数据）
- 默认 keymap：F13-F24 宏键 + 媒体键 + 旋钮音量 + 8 层（触摸键循环切层）
- 自定义键码：`JS_MODE`（摇杆切换 手柄/方向键/滚动）、`TP_TOG`（触摸开关）
- 注意：**按键语义是通用宏键盘**，没有 agent 专用键（接受/拒绝/PTT 等），需要自己改

## 6. 对我们的启示

### 可以借鉴

1. **Raw HID 帧设计**：固定 32 字节、命令/参数/校验边界清晰、PING→CAPS 握手。
   相比我们的串口 JSON 桥，Raw HID 免驱动、即插即用，更像"产品"。
2. **按链序寻址 + 设备端动画**：主机只推颜色状态，动画设备端生成。
3. **协议一致性测试**：oracle 驱动真实固件代码的测试方式。
4. **下单文档的完备度**：HOW-TO-ORDER 把 PCBWay 参数、备注话术、装配顺序写全，
   我们以后嘉立创打板可参考这个文档组织方式。

### 可以跳过

- 摇杆、触摸键（对 v1 是范围膨胀）
- VIA/Vial 共存复杂度（我们若走裸 QMK/MicroPython 不需要；若要用 Vial 改键才需要）
- 外壳美学打磨（v1 先保证能用）

### 我们需要补的（agentpad13 没有的）

- 主机守护：读 Codex 日志 → 推导状态 → 推颜色 —— **我们已有**（通道 B）
- PTT 语音输入 + 自动注入 —— **我们已有**
- agent 专用键语义（接受/拒绝/发送/PTT）—— 需改 keymap 或沿用我们的命令键布局

## 7. 风险与注意

- **许可证**：README 声明硬件 CERN-OHL-W-2.0、固件 GPL-2.0-or-later，但**仓库根部没有
  LICENSE 文件**（仅 README 声明）。GPL 固件改代码再分发必须开源；CERN-OHL-W 改设计
  文件需同类协议。直接买板组装不违反，改设计/固件再卖要遵守。
- **主机侧闭源**：`loudestd` 不在公开仓库，协议"单一事实源"拿不到；好在协议已完整
  记录在注释与 README，可自行按规范实现（我们本来就自己写）。
- **未完成项**：摇杆校准、模式持久化（RAM-only）、协议打包成 QMK Community Module
  都是作者列的 follow-ups，接手需自担。
- **供应链**：RP2040 货源、PCBWay 贴片最小起订、LCSC 部分料号库存波动。

## 8. 结论

agentpad13 的**硬件工程化和协议设计**是优秀参考，但：

1. 它的主机"脑子"（状态检测）闭源，而这恰是我们已完成的强项；
2. 我们不需要摇杆/触摸等特性，直接照搬会背不必要的复杂度；
3. 许可证约束 + 无 LICENSE 文件，商用改造前需要谨慎；

建议路线：**继续自研**（ESP32-C3 / 嘉立创打板），协议借鉴 Raw HID 帧结构；
如需快速出硬件原型，可参考其下单文档和 PCB 布局思路，但不直接采用其设计文件。
